## 1. What the renderer gives (Q8)
- EXISTING: re-render harness research/i5/rr.py replays a stored flight's GT poses through a standalone hyperlux (OptiX) renderer. hyperlux.camera exposes outputs RGB, Depth, Normals, Segmentation(labels='instance'), Flow(forward/backward), FlowStatus(forward/backward). MEASURED output layouts at 640x480, batch 16: Depth f32 [B,480,640], Normals f32 [..,3], Segmentation u32 instance ids, Flow f32 [..,2], FlowStatus u32.
- MEASURED: dense metric depth: yes, 100% pixel validity in the tested frames (valid_depth_frac 1.0), median depth ~1.7-2.1 m in rooms. Depth at arbitrary pixels is just indexing; arbitrary sub-pixel via interpolation (HYPOTHESIS, not tested).
- MEASURED convention: Depth is planar z-depth (along optical axis), NOT ray length. Test: unproject with the episode K (fx = fx_from_du to 6 digits, so intrinsics/camera row are consistent), transform by GT camera poses, reproject to previous frame, compare to renderer backward flow. Median flow error with z-depth: 5e-5-4e-4 px (p95 <7e-4 px) over 8 frames x 2 flights; with ray-length depth it is 0.02-3 px. So 3-D correspondences, depth-flow-pose consistency are exact to 1e-3 px.
- MEASURED: Flow('backward') is displacement in pixels from the current-frame pixel to its location in the previous frame (my test matched pix + flow vs reprojection into the previous camera). Forward flow did not match my backward-geometry formula (median 17-28 px) as expected, because I did not write the forward projection formula; not validated, treat forward flow as UNKNOWN until tested.
- MEASURED: FlowStatus values 0..4 occur; ~97% are 0 (valid), ~2.6% code 3, ~0.5% code 4 in a room frame. UNKNOWN: the exact code semantics (my guess HYPOTHESIS: 3 = occluded/disocclusion, 4 = out of view). Visibility/occlusion labels therefore exist but need a 10-line test to decode.
- MEASURED: normals unit norm (median norm 1.0). Segmentation = per-instance ids (27-42 distinct instances per frame in rooms), so object-instance masks are available; semantic classes are not (UNKNOWN whether glb node names carry floor/ceiling; HYPOTHESIS: floor/ceiling can be derived from normals.z and world height, or from instance names, since scenes load with preserve_instances=True).
- MATH (derived, not measured): 3-D correspondences without RGB = unproject depth (z-depth) at frame i, transform with GT poses to frame j, project; occlusion test = compare reprojected z with rendered depth_j at that pixel. Flow gives the same without needing depth_j.
- Meshes: scenes are conta assets (conta:<hash>) loaded via hyperlux.load_scene; mesh raycast depth is therefore not needed since the renderer already does it (EXISTING). Meshes themselves: not extracted (UNKNOWN whether the glb is readable outside hyperlux).
- Offline note: one forest flight failed at conta.resolve (conta tries to refresh its index over the network); with CONTA_CACHE set to gen/conta other flights loaded from cache. Harness runs need the cache dir env in run_test.sh.

## 2. Timing, exposure, poses (Q8)
- EXISTING: episode.json: pose timestamp = "mid_exposure"; camera 20 Hz, 1200 frames (60 s); IMU 200 Hz (12001 rows), GT 200 Hz (12006 rows) starting at t=-0.025 s; sub_frames k = ceil(exposure/5 ms) up to 10; blur_space linear/srgb; linear_gain, brightness_scale recorded (g3.py line 31). So sub-exposure poses are exactly the GT 200 Hz samples (5 ms grid), they are already stored.
- MEASURED: re-rendering at the mid-exposure GT pose reproduces the stored frame: Laplacian-NCC 0.996 (ro, k=1) at offset 0, and drops to 0.12 at +-1 IMU step (5 ms), 0.04 at +-2; so frame timestamps align with the GT grid to better than 5 ms and the image is a sharp function of the pose. wa flight: NCC 0.906 at offset 0 with stored mean brightness 153.8 vs rendered 125.0: geometry matches but photometric gain/tonemap is not reproduced by my replay (HYPOTHESIS: brightness_scale/linear_gain/exposure develop step in g3.py not applied; MEASURED only for the means). Unblurred frame: render at a single pose = exact (k=1 repro supports it); for k>1 blurred stored frames, the sharp frame at mid-exposure pose is the supervision for deblurring (EXISTING: g3 averages k sub-renders). I did not test the k>1 average reproduction; the code to do it is in rr.py (b) but the numbers did not get recorded (UNKNOWN).
- MEASURED (imu_check.py, 4 flights): IMU stamp vs GT: the best accel offset 0 or -1 IMU step and gyro -1 step (gyro convention: body rate over (i,i+1) vs stamped sample; ambiguity of one 5 ms sample, ~0.07 rad/s*... not resolved; flat residual curve: gyro resid 0.0706 at offset -1/0 vs 0.0737 at +-1, small difference). So the IMU/GT time convention is only determined to +-1 sample. 
- MEASURED: IMU noise residual std 0.28 m/s^2 (accel) and 0.070 rad/s (gyro) per axis, lag-1 autocorrelation ~0 (|r|<0.011): consistent with config accel_noise_std 0.28, gyro_noise_std 0.07, white. EXISTING config: accel_bias_init_max 0.2, gyro_bias_init_max 0.02, random walks 0.001 / 0.0006.
- True biases: NOT stored in the zips (EXISTING: only imu0, cam0, GT pose columns p,q plus episode.json; no bias column). MEASURED: recoverable by regression of IMU against GT-derived specific force/rate with a 5 s window: bias drift over the flight 0.01-0.06 m/s^2 and 0.003-0.016 rad/s (noise-limited: 0.28/sqrt(1000)=0.009 m/s^2, 0.07/sqrt(1000)=0.002 rad/s per 5 s MATH). Biases consistent with spec only roughly. If exact biases needed: regenerate with the simulator logging them (UNKNOWN whether the sim exposes them; EXISTING g3.py has no bias handling lines).
- True velocities: available from GT p by central differencing (MATH: 8-decimal positions => finite-difference acceleration rounding error ~3e-4 m/s^2, far below IMU noise 0.28; MEASURED decimals: p to 1e-8 m, q to 12 digits). GT "gt_decimals_ok" in imu_check.json is a hard-coded True, not a test; the decimals statement comes from reading the csv rows.
- Gravity: config gravity [0,0,-9.81]; state frame is gravity-aligned z-up (EXISTING). The scene frame differs by spawn scene_translation / scene_yaw (rr.py applies Rz, t); this was necessary and verified by NCC.

Per flight: ~30-60 s fixed + 1-20 s render => re-render batches should be grouped by scene (UNKNOWN: how many distinct scenes exist in out/keep; scene id is in meta).

- Re-render of existing flights with extra outputs: YES, feasible without regeneration (poses + intrinsics + scene id/translation/yaw from episode.json). Stored RGB cannot be reused from this; depth/flow for the same frames come from the re-render. MEASURED only for 640x480 (and 320x240 depth/RGB timing); resize-intrinsics: MATH: for resize by s, fx'=s*fx, cx'=s*(cx+0.5)-0.5 (pixel-centre convention, cx=319.5 for 640 => 159.5 at 320x? uses (319.5+0.5)*0.5-0.5=159.5). Not verified against stored 160x120 frames.
- Counterfactuals: (a) other FoV/intrinsics on the same trajectory: trivial, cam_row takes fov (EXISTING in rr.py; not rendered by me). (b) other exposure: re-average sub-renders at 5 ms GT poses (MATH-sound, NOT tested for k>1). (c) other texture/lighting/scale: needs scene editing in hyperlux; UNKNOWN. (d) new IMU noise realisations: yes, from GT: acc = R^T(a_w - g) + b + noise, gyro from body rates (MEASURED noise model matches; ±1-sample time convention unresolved, use offset 0 for accel and -1 for gyro as the data suggested); bias draw free. (e) counterfactual initial velocities: not by replay (a given path is fixed; HYPOTHESIS: slicing the path at another time yields a different start state; new velocity profiles on the same scene need the controller/sim, UNKNOWN).
- Fallback sparse depth by matching+triangulation: not needed (dense depth available), not tried.

## 4. Q9: precomputed geometric training set
- EXISTING: current corpus out/keep: 478 zips, 196 GB (about 410 MB/flight; 483 MB uncompressed for the sampled flight: 1200 640x480 grayscale PNG/JPEG frames + CSVs). The generator log has 11744 lines (flights generated so far, MEASURED line count). Disk is 99% used on /data (346 GB free, MEASURED df), so storage of derived data must be small.
- NEW EXPERIMENT / MEASURED: prototype shard of 48 flights (every 9th zip, 21+ of each of the three scene types), research/i5/shard/ (shard.py; out/ = 831 MB; list.txt, build.log). Per flight at 160x120: gray frames uint8 (23 MB raw), raw IMU, GT 200 Hz p,q,v, per-frame IMU preintegration (dR-vector, dv, dp, T; zero-bias, GT-free), KLT tracks (GFTT+LK, 80 max, ids), meta and config JSON. Size: mean 13.5 MB/flight (max 21.7 MB) compressed npz. Time on one core (cluster busy): read 0.04 s, decode+resize frames 9.6 s, preint 0.36 s, KLT 1.0 s, save 1.3 s, total 12.2 s mean (17 s max); 48 flights on 8 procs in 96 s wall => 0.5 flights/s... i.e. 2 s/flight effective.
- Scaling (MATH): 1000 flights => 13.5 GB (+ depth), 3.4 core-hours of preprocessing (about 25 min on 8 cores); 10k flights => 135 GB, which does not fit the 30 GB budget nor current disk free space: store at most ~1500 flights in this form, or drop to 80x60/crop, or store JPEG/uint8 and shard by flight windows. Adding f16 depth: 160x120x1200x2 B = 46 MB raw per flight (maybe ~15-25 MB compressed, UNKNOWN: not measured) => about 2.5x bigger. 320x240 depth 184 MB raw/flight, too large for more than a few hundred flights.
- Render cost for the depth/visibility labels (MATH from measured fps): 1200 frames depth-only 320x240 = 0.3-0.4 s + 15-40 s init => about 30-60 s/flight; 1000 flights ~ 10-17 GPU-hours serial, dominated by scene load/init and OptiX warm-up. Group by scene to amortise (HYPOTHESIS: large scenes dominate).
- Not built (UNKNOWN, cost only): MSCKF states/covariances/innovations require running the wasm estimator per flight (evalpool does this; cost per flight not measured here), quality scores, mid-flight window features. Window cropping with re-initialised frames: MATH/design: choose start frame s; reference frame = GT body pose at s with yaw zeroed (R0 = Rz(-yaw_s) R_s, gravity-aligned, matching the startup convention of the estimator); p0=0; v0 = R0^T applied to GT velocity at s (finite difference, ±1e-3 m/s); biases from the 5 s regression above (error ~0.01 m/s^2, 0.002 rad/s) or zero for the prior; preintegration recomputed from IMU rows >= s (already per-frame so windows are slices: preint of frames i..j needs composition, not stored per window; store per-frame increments and compose in the loader) ; tracks must be re-started at the window start (the stored track ids are flight-global, drop those first observed before s or accept longer tracks). None of this was run.
- Format recommendation (HYPOTHESIS, design): one npz/webdataset shard per flight; frames uint8 160x120 (or 128x96 crop), IMU float32, GT float32, per-frame preintegrations, tracks as flat (frame,id,x,y), optional depth f16 at 80x60 or 160x120, visibility/flow status bitmask; loader slices windows and does re-anchoring; I/O: 13.5 MB/flight, a 64-frame window reads ~0.7 MB if frames are chunked (not measured). Parallelism: decode-bound CPU stage trivially parallel per flight; render stage GPU, one process per GPU grouped by scene.
