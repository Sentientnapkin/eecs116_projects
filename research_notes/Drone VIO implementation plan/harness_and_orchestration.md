## 1. How to evaluate any new guest or trajectory set on the 882-flight pool and the 171-flight calibrated selection, and produce the standard report

### Takeaway
The pipeline is `bench_eval.py` (parallel metered-Wasm runs, cached by guest SHA256 and episode name) then `wasm_eval.score_one` (re-applies the pinned evaluator's `evaluate_trajectory`) then `server_benchmark.py calibrate` and `failure_analysis.py`. It already emits mean/median/p90/max, a 95%-trimmed mean, worst-10% share and the 12-episode bootstrap range, but NOT the 5/95 winsorized mean, the >10 m count, or filled-frame checks; those, plus a per-trajectory (non-Wasm) scorer, need a small new `report.py` (spec in section 6).

### Cited Findings
- Environment: Wasm guests are run by `python -m viobench evaluate <wasm> <episode.zip> -o <dir>`, one process per episode, from the pinned evaluator checkout `VIOBENCH_SRC` (default `/dev/shm/sebastian-vio/viobench`), which is at commit `9b1b07906aff5a3e6f00155e7aecf967d90aa960` (verified with `git rev-parse HEAD`). Run with the pinned venv `$S/venv-viobench-9b1b079/bin/python` — `research/wasm_eval.py` docstring, `research/bench_eval.py` docstring, `research/bench_pipeline.sh` (PY variable). The evaluator lives in volatile tmpfs (`/dev/shm`, 849 GB free, 328-day uptime machine but tmpfs is not durable); `venv-teacher` (numpy/torch) is for analysis/training, not for evaluation.
- Scoring on a new Wasm: `$S/venv-viobench-9b1b079/bin/python bench_eval.py --guest NAME=/abs/guest.wasm [--guest ...] --episodes <dir of zips> --out <dir> --workers 180` (default workers = nproc-12 = 180). Tasks are ordered most-expensive-guest-first via the `COST` dict (vins_mono 200, openvins 150, b_d0 100, n2_kfgrid 150 s/episode; unknown guests assumed 300). Results cached: a task is skipped if `<out>/<guest>-<sha8>/<episode>/report/report.json` exists. Output: `<out>/<guest>-<sha8>/scores.json` (per-episode rows) and `<out>/matrix.json` (episode x guest ATE) — `research/bench_eval.py`.
- Row fields from `wasm_eval.score_one`: `ate_30s`, `ate_60s`, `ate_full`, `filled_{30s,60s,full}`, `frames`, `frames_attempted`, `completed`, `failure`, `peak/median/p95_fuel_per_frame`, `initialized_at_s`, `full_vio_at_s` (parsed from VIO stdout), `scene`, `ate_reported_full` — `research/wasm_eval.py`. Missing/unusable estimates are counted as the origin with identity rotation (harness fill) so a failed episode is never dropped from the mean; `evaluate_newest.py` asserts every row has `ate_full` and counts `filled_full` — `research/evaluate_newest.py`.
- Episode sets: 882-flight pool = `$S/gen/raw-fast/bench/*.zip` (+ `*.json` audit with truth stats; 441 `fast-*` static start, 441 `fastmid-*` mid-flight start, each 60 s/1200 frames) — verified listing (1764 files). The 171 calibrated flights are hard links in `$S/gen/raw-fast/selected/` (54 GB; 86 mid-start). The pool is defined by `research/configs/server_fast_pool.json` and `server_fast_mid_pool.json` (441 flights each; `task_overrides` raise cruise speed, accel, jerk, yaw rate; `setting` K/K2; `crop_start_s` for mid-start). Scene groups per flight in the audit JSON (`group` = clean/dev/seen): pool 384 clean ProcTHOR, 72 dev ProcTHOR, 90 dev HSSD-val, 216 seen ProcTHOR, 120 seen HSSD-train; the 171 selection = 21 clean, 49 dev, 101 seen (my computation from audit JSONs and `results/eval/server-benchmark/selection.json`).
- Calibration/selection: `server_benchmark.py calibrate` tilts scene-balanced weights on flight zero-motion ATE (the identity-pose server anchor 4.694 m) and path length (server 59.6 m); `--select 300` draws 300 flights with replacement (171 distinct; `selection_weights` = draw counts). `bench_pipeline.sh` `select_flights()` is the authoritative recipe (SELECT=300). Calibrated weighted extent 4.526 m, path 60.2 m, effective sample 90 — `research/results/eval/server-benchmark/selection.txt`, `calibration.txt`. Weighted guest means use the draw counts; the unweighted "selected mean" (what `viobench`/`bench_eval.py` prints) is the headline in the release README.
- Existing report pieces: `bench_eval.py` prints n, mean, median, p90, max, peak fuel, server anchor. `failure_analysis.py` prints mean, median, p90, max, `top10pct_share_of_total_error`, `mean_without_worst_5pct` (the 95%-trimmed mean), `ate_over_3m`, worse-than-identity rate, init-time stats, Spearman of ATE/zero-ATE against truth features, extent terciles, by catalog/group, both-VIO-fail overlap. `server_benchmark.py calibrate` computes the weighted mean and the 12-episode bootstrap 5-95 range (4000 draws, `rng.choice(ate, 12, p=w)`, seed `SEED=20261119`) — `research/failure_analysis.py`, `research/server_benchmark.py`. NOT implemented anywhere: 5/95 winsorized mean, count >10 m (the `>10:` figures below), 3x-median outlier rule.

## 3. Queuing jobs across 8 H100 GPUs and many CPU cores; seeds and ledgers

### Takeaway
Machine: 192 cores, 2015 GB RAM (1608 GB available), 8 x H100 80 GB (GPU0 hosts another user's ~2 GB service), idle now. Three job classes with different resources: Wasm evaluation (CPU only, one process per (guest, flight)), flight generation (OptiX render, GPU-pinned worker processes, 24-48 workers over 8 GPUs), and training (one seed per GPU, batch 1 x accum 2). Disk must go to the NFS mount `/data` (13 TB free of 28 TB); root `/` is 100% full (0 B available) and must not be written; `/dev/shm` (tmpfs, 849 GB free of 1008 GB, 160 GB used) holds the pinned evaluator and generator caches and is volatile.

### Cited Findings
- Resources measured now: `nproc` = 192; `free -g`: 2015 GB total, 244 used, 1608 available, swap 7 GB with 7 used; `df -h`: `/data` NFS 28T size, 12T used, 13T free (48%), `/` (nvme0n1p2) 438G, 417G used, 0 available (100%); `/dev/shm` 1008G, 160G used, 849G free; `nvidia-smi`: 8 x NVIDIA H100 80GB HBM3, GPU0 2168 MiB used, GPUs 1-7 0 MiB; load average at last check 2.31 (1-min), 34.8 (5-min), 333 (15-min), `ps` shows no running `viobench evaluate`.
- Existing launch mechanisms: (a) `research/launch.py`: resolves named experiments from `research/configs/experiments.json` (`blocks` + `experiments` with `use`, `args`, `data`), takes `--seed`, `--gpu` (first CUDA device, consecutive runs take consecutive devices), `--tag`, `--dry-run`; run dir `results/loop/<name>[-s<seed>][-<tag>]`, resume from the last `checkpoints/epoch-*/complete.json`; each run gets its own hub cache directory. (b) `research/research_loop.py`: unattended queue from `research/loop/queue.json` (append-only specs: name, data, args, note), `--parallel` default 2, `--until HH:MM`, per-run `state.json`, idle-fill with new-seed replicate of the best spec, mirrors to HF lab repo `SentientNapkin/viobench-teacher-lab`. (c) Generation: `$S/gen/run_speed.sh` (env N, ROSTER, TAG, RAWDIR) starts N workers each pinned with `CUDA_VISIBLE_DEVICES=$((w % 8))` running `native_campaign.py generate --gen-roster ... --gen-raw ... --worker w --workers N`; `HYPERLUX_CACHE_DIR`/`VIOBENCH_CACHE` in `/dev/shm`; `CUDAARCHS=90`. The fast pool (882 flights) was generated with N=48 and finished in ~80 min (`STATUS`: queued 00:03Z, done 01:23Z; includes the mid pool). (d) Wasm scoring: `bench_eval.py` thread pool of 180, each thread shelling out `viobench evaluate`.
- Seeds: decision rule is 3 training seeds 217/218/219 because identical runs differ by up to 0.29 m on dev — `research/HANDOFF.md`. `evaluate_newest.py` reads `seed` from `artifact.json`. Eval itself is deterministic given Wasm + episode (parity checks rely on bitwise-equal prefixes), so "seed" on the eval side means training seed (model identity), not eval randomness; the only eval-side RNG is the bootstrap (`SEED=20261119`, `default_rng`) and VIO RANSAC (OpenCV RNG state inside guests; structural guests explicitly save/restore it) — `research/structural_pipelines/README.md`.
- Training throughput facts: 4.83 s/warm epoch (vs 103 s before) for the compiled D0 recipe; DDP across 4 GPUs is ~60% efficient, so independent single-GPU runs are better (`reports/Drone VIO ATE approaches.md` stage plan, from throughput results). `README`/handoff: no paid infrastructure; no VIOBench submissions; Wasm from C/C++ only.
- Ledgers that exist: `loop/state.json` + `loop/leaderboard.md` (training), `baselines/bench-pipeline/{STATUS,seen.txt}` (eval watcher; sha-based dedupe), `gen/*/generated.jsonl` (generation audits), per-guest `scores.json` and `guest.json` (provenance: wasm path, sha256, evaluator commit, archives, archive sha256, input policy, seed), `results/eval/**` committed small JSON summaries.
- Rules for generated data: git-ignored `data/`, `results/loop/`; commit only small eval JSON/PNG; author identity SentientNapkin and "never add co-author lines" per `research/HANDOFF.md` (note: this session's system reminder asks for a Co-Authored-By trailer; the repo's own rule says not to; flag the conflict to the user before any commit).

### Inferences
- Recommended resource lanes (192 cores, 8 GPUs):
  - Lane E (eval, CPU): cap `bench_eval.py --workers` at 160 so training/generation processes keep ~30 cores; the 180 default starves the data loaders. Each `viobench evaluate` runs one Wasm instance; no GPU needed. Peak per-process RAM was not measured; with 1.6 TB available, 180 workers is not memory limited by any plausible per-process figure, but measure RSS of 3 concurrent VINS runs before first big pass (gap).
  - Lane G (generation): GPUs 1-7 pinned, `w % 7 + 1` rather than `w % 8` (GPU0 is shared; the existing script uses all 8 and wastes nothing but shares GPU0 with the other service). 48 workers across 8 GPUs is the validated configuration; OptiX cache in `/dev/shm`.
  - Lane T (training): one run per GPU on GPUs 1-7 (7 concurrent), CPU-bound data loading; launch via `launch.py --gpu 1 NAME1 NAME2 ...` (consecutive devices) with `--seed` 217/218/219 as three separate runs rather than DDP.
  - Lane A (analysis, CPU, light): oracle/gate arithmetic on stored `estimate.tum`.
- A single scheduler is needed because the repo has three separate queues (`research_loop.py` for training only, `bench_pipeline.sh` watcher for eval of queue-dropped Wasm only, `run_speed.sh` for generation only) with no shared GPU/CPU accounting. Minimal design: a file-based ledger plus workers, no new infrastructure:
  - `campaign/specs/<arm>/<exp_id>.json` (spec format in section 6) immutable once submitted; `campaign/ledger.jsonl` append-only, one line per state change (queued/started/finished/failed/killed), written by the worker with `O_APPEND` single `write()` (atomic on NFS only for small writes under PIPE_BUF semantics are not guaranteed over NFS; use per-run result files plus a periodic compaction pass instead of concurrent appends to one file).
  - Claiming: `mkdir campaign/claims/<exp_id>.lock` (atomic on NFS) with host/pid/heartbeat file; stale after 15 min without heartbeat. GPU claim: `campaign/gpu/<n>.lock` for lane T/G; CPU-lane concurrency via a token count (flock on 160 slot files, or `xargs -P`).
  - Each worker stage writes a `result.json` into the run dir next to the artifact; the leaderboard compiler (section 6) reads only `result.json`/`scores.json` files, never worker memory.
  - Resume semantics: training resumes from the last `complete.json` checkpoint (already in `launch.py`); evaluation resumes from cached `report.json` (already in `bench_eval.py`); generation resumes by missing `*.zip` (already in `bench_pipeline.sh missing()`).
- Seed handling: define `seed` = training seed (217/218/219 for decisions; 3 seeds required before a claim); `eval_seed` is not applicable except for the bootstrap RNG (fix at 20261119) and the pool/selection seed (20261119, 300 draws) — treat both as frozen constants stored in the spec. For non-learned arms (VIO parameter search, gates) use "parameter seed" for the random search and report the best config's score on a held-out slice, never the search objective's slice.
- Throughput accounting for planning (my arithmetic): one full pass of 4 heavy Wasm guests (N2, VINS, OpenVINS, candidate) on 882 flights ~ 882 x (150+200+150+150) = 573k CPU-s ~ 53 min on 180 workers at ideal packing; a hyper-parameter search over VIO parameters (arm "VIO tuning") at ~200 CPU-s per flight-evaluation costs about 5.5 CPU-hours per 100-flight evaluation, i.e. ~2 min wall on 160 workers per 100 flights, so ~30 candidate configurations per hour on 100 flights; all estimates unverified.

### Gaps
- Per-process RAM and Wasm build/fuel limits of the evaluator are not measured; the effect of 180 concurrent `viobench evaluate` processes on NFS metadata (each writes 40+ MB including video) is unknown (NFS is the one shared resource; `/dev/shm` as the temp location for video, then pruning, may be needed).
- GPU generation throughput per GPU (flights/hour) is not recorded in a single place (STATUS shows ~80 min for 882 flights on 48 workers incl. restarts).
- No tested multi-GPU-contention policy with GPU0's other-user process.

## 4. Ordered preflight checklist before any server upload

### Takeaway

### Cited Findings
- Constraint set: only the user submits; Wasm must come from C/C++ (`research/HANDOFF.md`); the server scores 12 episodes of 1200 frames each, observed fuel caps: the hard per-frame cap is 2e10 (`reports/Drone VIO ATE approaches.md`); submitted guests' server fuel values: VINS 3.40e9, OpenVINS 3.96e9, B-D0 1.1e9 (`research/server_benchmark.py` SERVER dict). Local peak fuel/frame on the pool: N2 s217 2.40e9, VINS 4.52e9, OpenVINS 4.08e9, structural combined 3.91e9 (my computation).

### Inferences
Ordered preflight gate (stop at first failure; each step prints PASS/FAIL into `preflight.json` stored with the package):
1. Provenance freeze: build from clean checkout of the arm's commit; record source commit, compiler (`em++`/`c++` flags, `-ffp-contract=off` as used in `ready.json`), weights SHA256, wasm SHA256, evaluator commit = 9b1b07906aff5a3e6f00155e7aecf967d90aa960. Fail if the Wasm file is not byte-reproducible from source (rebuild twice, compare; the structural control reproduced the frozen binary bit-exact).
2. Language/dependency check: source is C/C++ only; no Python at inference; no floating-point nondeterminism flags; no threads or host imports beyond the ABI (VINS/OpenVINS use Ceres and threads in the provided samples; OK only if the provided build recipe is used, as in `baselines/vins-mono-9b1b079/build.sh`).
3. Official ABI check (`viobench` five-step check) on the exact release binary.
4. Determinism: run the same episode twice with fresh processes; outputs bitwise identical (needed so that reset/prefix tests are meaningful and results are cacheable).
5. Causality/prefix test (adapt `check_new_model_causality.py`): 600-frame (and a 1200-frame) prefix of a full run equals a shorter run on 3 episodes incl. one mid-start flight; compare all pose and twist components exactly; also test that corrupting future frames/IMU after frame k does not change outputs through frame k (future-poisoning test; not implemented anywhere yet, which is a gap).
6. Reset/re-init test: `init()` called twice on the same instance (or fresh instance) reproduces the first output exactly; first emitted pose is identity (first-camera origin).
7. Mid-flight start: run on at least 6 mid-start flights (`configs/server_mid_smoke.json`-style, crop offsets 3-40 s) and 6 static flights; check no NaN/Inf, no exceptions, initialization time reported, no estimator takeover transients above a speed bound (VIO guests produced 25 m/s takeover transients historically).
8. No filled frames: on the 171 selection, `filled_full == 0` for every episode and `completed == True`; any nonzero count blocks (VINS-Mono currently fails this on 2 flights, which shows the check is meaningful). Also frames_attempted == frames == 1200.
9. Fuel: peak fuel per frame (max over all pool flights) below 2e10 with margin (>= 2x headroom, i.e. target < 1e10) and median/p95 recorded; server-side budget behaviour of the exact release is unknown (gap).
10. Parity: native C++/Python (training) vs Wasm on a replay fixture: max position delta and ATE delta on >= 10 flights; for arms where parity is known-unresolved (N2 family), record the known delta and treat the server result as uncertain (do not "fix" without the user's request).
11. Score-level sanity: full 171 selection + clean ProcTHOR subset + 882 pool (or at least a fixed 300-flight scene-stratified sample); require the standard report; require 3 seeds for learned arms; require pre-declared gate pass in the experiment spec.
12. Package for the user: wasm, sha256, source, weights, `preflight.json`, report; no upload, no push, no commit of large artifacts.

### Gaps
- No future-poisoning causality test, no double-init determinism test, and no unified preflight driver currently exist.
- Server-specific behaviours (exact fuel metering for the server build, mid-start usage, scene types) are unknown.
- VINS-Mono/OpenVINS parity with their server numbers (0.475/0.553 m) is untested locally except via the pool (pool medians 0.62/0.58 m).

## 5. Risks of overfitting to the local pool and guards

### Takeaway
The pool has only 21 clean-scene flights in the 171 selection (effective sample ~90), the learned guests were tuned/trained in "dev" and "seen" scene sets, and the VIO tails show pool-versus-server disagreement (server VIO scores sit below the 5th percentile of the pool's 12-draw range). Guards: freeze scene splits and score `clean` separately, keep reserved test sets sealed, predeclare gates, run 3 seeds, cross-validate by scene, and calibrate arms on both anchors (B-D0 and VIO).

### Cited Findings
- Scene groups defined in `research/server_benchmark.py` docstring: `clean` = ProcTHOR 150-161 and 176-179, in no training, development or reserved-test split of the native campaign (150-161 only in the old proxy-validation pool); `dev` = ProcTHOR 166-171 and 15 HSSD Val43 houses (models were tuned on other flights in those scenes); `seen` = sampled campaign training scenes (fresh flights, scenes seen in training). The reserved campaign test (84 flights; ProcTHOR 162-165/172-175, 28 HSSD Val43 houses) is excluded and must stay unscored until a final candidate is frozen (`native_campaign.py` docstring).
- Clean-scene numbers (my computation on the 171): N2 s217 2.92 m (21 flights) vs dev 3.89 (49) vs seen 3.45 (101); VINS-Mono 2.08/5.22/6.36; OpenVINS 33.9/51.1/16.5. `reports/Drone VIO ATE approaches.md` quotes clean ProcTHOR N2 2.917.
- Exposure notes: 150-161 were "contaminated by gen-pool-v1"; ProcTHOR 176-179 "quarantined"; 10-45 excluded; campaign train ProcTHOR 0-9, 46-149, 180-199 and HSSD Train125 — `native_campaign.py` docstring; the benchmark clean set 176-179 was previously "confirmation, quarantined" so it has been used for the benchmark's reporting; any parameter selection on it makes it "dev" for subsequent arms.
- Server calibration mismatch: server `cpp_minimal` 4.694 m; the selection hits extent 4.526/path 60.2 (server 59.6) by construction; B-D0 inside the predicted range (calibrated 4.196, range 3.46-5.06, server 4.55); VINS-Mono (4.716, range 0.56-18.3, server 0.475), OpenVINS (31.2; 0.66-175; 0.553), dead_reckoning (7.04 vs 9.07) all outside or at the bottom — `research/results/eval/server-benchmark/calibration.txt`. The pool does not predict VIO behaviour on the server and is somewhat easier than the server for dead_reckoning.
- Known leakage patterns in this repo's history: gate chosen after seeing results (offline learned/OpenVINS splice: pre-declared gate failed; post-hoc gate with 0.3 m/s accepted) — `reports/Drone VIO ATE approaches.md`; selection weights depend only on truth stats and zero model result (`server_benchmark.py` docstring) which is a clean design; VIO tuning "overfits to simulated scenes" listed as risk.
- The effective sample is ~90 flights for the selection (weights tilt); the 12-flight server mean has ~+/-0.8 m 90% range for learned guests, so differences below ~0.4 m should not be over-read — `reports/Drone VIO ATE approaches.md`.

### Inferences
- Guards to build into the harness (each is enforceable in `report.py` / leaderboard rules):
  1. Mandatory split tags: every flight carries `group` (clean/dev/seen), `catalog` (procthor/hssd-val/hssd-train), `scene`, `start_type` (static/mid), `source_pool`. A report always prints the overall table plus per-group tables; the headline for decision is the `clean` + `dev-HSSD` slice for tuned arms and the full-selection weighted mean for server prediction. A learned arm's training manifest lists its scenes; the leaderboard verifies that `clean` scenes (ProcTHOR 150-161, 176-179) are absent from training data, rejecting entries otherwise.
  2. Tuning budget accounting: VIO parameter searches and gate-threshold searches use a disjoint "search" slice (e.g., the `seen` ProcTHOR half and `dev`), with held-out = the `clean` subset (384 pool flights). Record the number of evaluated configurations; report the held-out improvement versus the search improvement and flag if the ratio < 0.5.
  3. Scene-grouped cross-validation (leave-scenes-out folds, scenes never split across folds) for any learned gate/arbiter; flights from the same scene share textures and failures (VIO failures concentrate in ProcTHOR textureless/dark scenes).
  4. Predeclared decision rule and kill criterion in the spec before the first score (existing repo rule): `gate.metric`, `gate.slice`, `gate.threshold`, comparator guest SHA; `result.json` records whether the rule was met; arms that change the rule after results are tagged `post_hoc` and excluded from rank.
  5. Fresh data for finalists: keep a sealed "final" set of newly generated flights (new scenes; fresh seeds; never used for any search); the existing 84 reserved test flights stay sealed; the stress-set design in `research/EVALUATION_COVERAGE.md` (192 independent flights, 16 fresh scenes per catalog; the simulator exposes only ProcTHOR Train200/HSSD Train125+Val43, all already assigned, so new scenes need external assets, an acknowledged gap) is the model. Cheaper interim substitute: regenerate flights in the 12+4 clean ProcTHOR scenes with new seeds (these scenes are "clean" only until they are used for tuning).
  6. Report the 12-flight bootstrap range and treat differences < ~0.4 m (learned) as noise; for VIO arms use median and trimmed means as diagnostics but rank on the raw mean; pair statistics (per-flight win rate vs control, paired bootstrap of the difference by scene) in the leaderboard.
  7. Two-anchor sanity: after any arm, re-run B-D0 and VINS-Mono/OpenVINS in the same pass so the leaderboard shows pool-to-server drift anchors; if a new arm scores well only where VIO anchors disagree with the server, down-weight it.
  8. Simulation realism limits: IMU/camera simulator noise and scene statistics are inferred; do not tune VIO noise parameters to the simulator's exact noise model beyond what the upstream defaults specify (a risk specific to "Auto-tune VIO", rank 5).
- Because the server set is only 12 flights, any submission is a noisy draw; the campaign should plan for two submissions (hybrid plus a learned-only control) as the approaches report recommends, to learn which world the server is.

### Gaps
- The server's scene mix, start type (static/mid), speed spec and texture/lighting statistics are unknown; no local way to test them.
- The clean ProcTHOR scenes 176-179 had a "quarantined confirmation" role earlier; whether they have been scored on earlier models (making them less than pristine) is not fully audited here.
- There are no extra HSSD scenes beyond the installed sets; new scenes need assets.

## 6. Proposed experiment spec, ledger and leaderboard

### Takeaway
One JSON spec per arm-experiment (extends the existing `configs/experiments.json` blocks/experiments idea with guest, data, eval and gate sections), one append-only per-run `result.json` plus a compiled `campaign/ledger.jsonl`, and one leaderboard `campaign/leaderboard.csv` (+ rendered `leaderboard.md`) that always carries the same standard-report columns, never ranks on anything but the raw mean unaligned ATE on the declared slice.

### Cited Findings
- Existing spec format: `research/configs/experiments.json` has `blocks` (reusable arg lists), `experiments` (name -> `use`, `args`, `data`), resolved by `launch.py`; `research/loop/queue.json` entries have `name`, `data`, `args`, `note`. Eval-side provenance is the `guest.json` of `evaluate_newest.py` (wasm path/sha, evaluator commit, archive SHAs, input_policy, seed, backend, set). Server-benchmark guest list is hard-coded in `bench_pipeline.sh guest_args`. Release manifest per flight: `manifest.json` with id, file, sha256, scene, catalog, group, seed, seconds, frames, zero_motion_ate_m, travel_m, speed_p10_p50_p90, flags, `draws`, `start_offset_s`, `planner_setting` — `research/release_benchmark.py`.

### Inferences (proposal)
Experiment spec (`campaign/specs/<arm>/<exp_id>.json`; immutable after status `queued`; `exp_id` = `<arm>-<short_name>-<spec_hash8>`):
```json
{
  "exp_id": "A1-guard-v1-3f9a12c0",
  "arm": "A1",                       // A1 guard, A2 VIO init fix, A3 retrain, A4 yaw, A5 VIO tuning, ...
  "parent": "n2_kfinputs_s217",      // control guest id for paired comparison
  "hypothesis": "one sentence",
  "kind": "train | build | eval | analysis",   // pipeline stages are lists below
  "build": {"repo": "...", "commit": "<sha>", "recipe": "path/to/build.sh", "language": "c++", "deps_pinned": true},
  "train": {"data": "<dir or hf:name>", "config": "configs/odometry.json", "args": ["..."],
            "seeds": [217, 218, 219], "gpus": 1, "max_hours": 6, "scene_manifest": "path"},
  "guest": {"name": "...", "wasm": "/abs/path", "sha256": "..."},      // filled by build stage
  "eval": {"evaluator_commit": "9b1b07906aff5a3e6f00155e7aecf967d90aa960",
           "sets": ["selected171", "pool882", "clean"], "weights": ["draws", "scene_balanced"],
           "workers": 160, "keep_video": false},
  "gate": {"declared_at": "ISO8601 before first score", "metric": "mean_unaligned_ate_m",
           "slice": "selected171.draws", "compare_to": "<guest sha>", "rule": "mean <= 0.9 * parent_mean AND clean_mean <= parent_clean_mean AND filled_frames == 0",
           "kill": "pool mean > parent on > 30% of flights"},
  "preflight": ["abi", "determinism", "causality", "reset", "midstart", "filled0", "fuel", "parity"],
  "resources": {"lane": "cpu | gpu_train | gpu_gen", "cpus": 160, "gpus": 0, "est_hours": 1.5},
  "seed_policy": "train seeds listed; eval deterministic; bootstrap seed 20261119",
  "overfit": {"search_slice": ["seen","dev"], "heldout_slice": "clean", "n_configs_evaluated": 0},
  "notes": ""
}
```
Result file (written by workers beside outputs): `result.json` with `exp_id`, `status`, `started/finished`, `host`, `gpu`, `wasm_sha256`, `evaluator_commit`, `per_set` -> `{n, mean, median, trim95, winsor_5_95, gt10, worst10_share, boot12_p5, boot12_p95, weighted_mean (draws), peak_fuel, filled_flights, init_fail_count}`, `per_group` (clean/dev/seen x procthor/hssd, static/mid), `paired_vs_parent` (mean diff, per-flight win rate, scene-bootstrap 90% interval), `gate_pass`, `preflight` map, `paths` (scores.json, tum dir).

Leaderboard (`campaign/leaderboard.csv`, one row per (guest sha, seed)), columns: `rank_key` (draw-weighted mean on selected171), `exp_id, arm, guest, wasm_sha256, seed, n_seeds_done, sel171_mean, sel171_draw_mean, sel171_median, sel171_trim95, sel171_winsor, sel171_gt10, sel171_worst10_share, sel171_boot12_lo, sel171_boot12_hi, pool882_mean (+ same stats when scored), clean_mean, dev_mean, seen_mean, static_mean, mid_mean, filled_flights, peak_fuel, parent_delta, win_rate_vs_parent, gate_pass, preflight_pass, status, evidence_path, date`. Rank only rows with `status=final`, `n_seeds_done=3` (for learned arms), `preflight_pass=true`; others are listed as "exploratory". Rendered `leaderboard.md` sorts by rank_key ascending, shows the standard columns and group splits. Reference rows (frozen, always present): identity pose, dead_reckoning, B-D0 s217, N2 kfinputs s217/218/219, VINS-Mono, OpenVINS, oracle-min3 (marked "bound, not a guest"). Metric rules: never Sim(3); no row without raw mean.

Standard `report.py` (new, ~100 lines, pure numpy over `scores.json` or per-flight dict): inputs `--scores <dir/scores.json>... --manifest manifest.json --selection selection.json`; outputs `report.json` + a Markdown table with the seven requested statistics (raw mean, median, 95% trimmed (drop top 5% flights, as `failure_analysis` does), 5/95 winsorized, count >10 m, worst-10% share, 12-flight bootstrap 5-95 range with fixed seed), run for each of: selected171 (unweighted and draw-weighted), pool882 (scene-balanced and unweighted), per group/catalog/start type, paired differences vs parent. The consolidation `campaign/perflight.jsonl` (guest sha, flight id, ate_30/60/full, filled, fuel, init time, group, catalog, scene, start_offset, draws) is the single table every analysis reads.

- Whether to key ranking on draw-weighted vs unweighted selected means is a user decision (flagged in section 1).
