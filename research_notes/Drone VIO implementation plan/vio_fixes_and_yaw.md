# Code-level fixes for geometric VIO failure modes and learned-model yaw drift

Conventions. Metric is mean unaligned ATE (m). "OV" = provided OpenVINS example (3-hypothesis Ceres fixed-lag smoother), pinned viobench `9b1b079`; source read at `/data/backups/rganapa/Sebastian/viobench-provided-openvins/viobench/solution/examples/native/openvins/` (call it `OV/`) and `.../vins_mono/` (`VM/`). Repo prior notes: `/data/backups/rganapa/Sebastian/eecs116_projects/research_notes/Drone VIO ATE approaches/` and `/data/backups/rganapa/Sebastian/eecs116_projects/reports/Drone VIO ATE approaches.md`. Repo was read-only; scratch scripts are in the session scratchpad (`manh.py`, `revisit.py`). No private server episodes were touched. All repo-derived facts cite a file path; "my measurement" = computed this session on local generated flights in `/data/backups/rganapa/Sebastian/gen/raw-fast/selected` (171 flights, 94 ProcTHOR / 77 HSSD).

Two framing facts that change the ranking (details in sections below):
1. VINS-Mono "status -1" is not mostly a numerical crash. Upstream `failureDetection()` calls `clearState()` (reboot), and the viobench wrapper deliberately throws on any reboot after metric output began, so every upstream-triggered reboot becomes a permanent -1 and (per the evaluator's hold-last policy) a frozen trajectory. This is fixable in about 40 lines in `VM/solution.cpp`.
2. OV's output path has no sanity check between the smoother state and anything else: the moment `graph.state_at()` returns true, the smoother's position/velocity replace the EKF's (`OV/solution.cpp` L379-396), and `consensus_output.h` L149-165 takes a geometric median of three smoothers that share the same initial state/frontend (correlated), so it cannot reject a common-mode transient. A 10-20 line guard here directly targets the 25 m/s transients.

## 1. Late/failed initialization and the ~25 m/s takeover transient (OV and VM)

### Takeaway
The two worst, fixable defects are (a) pre-init output is zero translation and the first-camera origin is recovered by back-integrating raw IMU over the whole pre-init period (up to 107 m origin error measured on a 19.65 s late init), and (b) there is no velocity/acceleration/innovation gate on the smoother output at takeover. Both can be bounded using the already-available N2 learned velocity (bounded ~3.5 m on the 60 m pool, error uncorrelated with VIO error), at low engineering cost.

### Cited Findings
- Server-calibrated pool failure statistics: OV mean ATE 0.98 m if initialized within 3 s versus 168 m otherwise; VINS-Mono 3.39 versus 9.84; init median 1.9 s for VINS; OV 17/171 flights over 10 m carry 96% of error — [project_history.md](/data/backups/rganapa/Sebastian/eecs116_projects/research_notes/Drone%20VIO%20ATE%20approaches/project_history.md), [report](/data/backups/rganapa/Sebastian/eecs116_projects/reports/Drone%20VIO%20ATE%20approaches.md).
- Campaign: OV initialized 114/120, 0.90-24.55 s after first camera; late static init after hover gives a 1-3 s velocity transient up to 6-25 m/s; diagnostic worst flight showed gyro bias [-0.0823,-0.0193,0.0208] rad/s at init and smoothers diverging with zero active visual factors; delayed moving init `dev-106878858_174886965-00-crop5` had 19.65 s delay and 107.192 m backward-integrated origin displacement; initial speed >=0.20 m/s group: capped30 11.575 / full 17.301 versus <=0.05 group 4.180 / 36.548 — [BASELINE_FINISH_REPORT.md](/data/backups/rganapa/Sebastian/eecs116_projects/research/BASELINE_FINISH_REPORT.md).
- Pre-init behaviour of OV: gyro-integrated attitude, zero translation; origin recovered by `imu_pose_at_first_frame()` which integrates buffered IMU back from the initial state with the initializer's biases (`OV/solution.cpp` L279-292, L355-361; README "From OpenVINS' state to the ABI").
- Takeover path: `write_graph` lambda uses `graph.state_at(t, smoothed)` and overwrites rotation/position/velocity/gyro bias whenever it returns true, with no comparison to the EKF (`OV/solution.cpp` L379-396). Each smoother is initialized once from the EKF state + covariance (`fixed_lag_vio.h::initialize` L161-185); `optimize()` accepts a step if `final_cost <= initial_cost` and otherwise restores (L464-486).
- Consensus is an equal-weight geometric median of 3 correlated hypotheses; the README states they "are correlated hypotheses, not independent measurements" (`OV/consensus_output.h` L149-165, `OV/README.md`).
- OV static init requires >=15 tracked features for the disparity test (so textureless views block rather than fake static init), mean disparity <= `init_max_disparity` 1.5 px on both half-windows, IMU std <= `init_imu_thresh` 1.0 — [InertialInitializer.cpp L108-134 (OV host-build source)](/data/backups/rganapa/Sebastian/viobench-provided-openvins/host-build/src/open_vins/ov_init/src/init/InertialInitializer.cpp); dynamic init needs `init_dyn_min_deg = 5` deg excitation, 6 poses, `init_dyn_inflation_*` = 10/100/10/100 (`OV/solution.cpp` L146-152).
- VM initialization: upstream visual-inertial alignment (SfM + gyro bias + gravity + scale) plus stationary bootstrap (|acc|-g <0.4, |gyro|<0.05, median/p90 disparity <1.5/2.5 px) added by the viobench patch (`VM/patches/vins_mono.patch` L119-139); upstream returns false on "misalign visual structure with IMU" and its IMU-excitation check is commented out (return false disabled) — [VINS-Mono estimator.cpp](https://raw.githubusercontent.com/HKUST-Aerial-Robotics/VINS-Mono/master/vins_estimator/src/estimator.cpp).
- PNEC initialization: rotation-translation decoupled framework with a probabilistic-normal-epipolar-constraint gyro-bias estimator, then velocity/gravity/scale fusion and refinement; EuRoC reductions of 16% gyro-bias error, 4% rotation error, 29% gravity error; TUM 14.2% gravity, 5.7% scale; accepted RA-L; code https://github.com/MUCS714/DRT-PNEC — [arXiv 2410.19473](https://arxiv.org/abs/2410.19473). Baseline for the "29%" is not stated in what I read; it compares to VINS-Mono/DRT variants per prior notes.
- Inertial-only MAP initialization (ORB-SLAM3 lineage): initialization as MAP estimation with IMU uncertainty, <4 s on EuRoC at almost any point of the trajectory, average scale error 5.3% — [Campos et al., arXiv 2003.05766](https://arxiv.org/abs/2003.05766).
- DM-VIO: delayed marginalization plus pose-graph BA for IMU initialization; strongest monocular design on TUM-VI per its paper — [arXiv 2201.04114](https://arxiv.org/pdf/2201.04114). Learned monocular depth priors in initialization: [arXiv 2204.09171](https://arxiv.org/pdf/2204.09171).
- Measured (this session): in the 171-flight pool the drone does not hover long; hover_seconds=1.0 per `episode.json`, mid-start flights (`fastmid-*`) start in motion, so "static init" is structurally unavailable for them (`/data/backups/rganapa/Sebastian/gen/raw-fast/selected/*.zip`, `episode.json` config.episode.hover_seconds).

## 2. Accelerometer-bias (and general) runaway

### Takeaway
The observed runaways occur "with zero active visual factors" (BASELINE_FINISH_REPORT), so the real defect is that nothing constrains the smoother when vision disappears. Add (a) a visual-factor-count watchdog, (b) bias and velocity clamps at the same level VINS-Mono's own `failureDetection` uses (acc bias 2.5, gyro bias 1.0, translation jump 5 m) but with a graceful fallback, and (c) a Mahalanobis gate on the output.

### Cited Findings
- Early-init slow runaways: 169-04 0.8 -> 12.8 -> 231 m/s reaching 2,232 m; 168-03 411 m; true speed <0.404 m/s; EKF velocity ~0.236 m/s while smoothers diverged — [BASELINE_FINISH_REPORT.md](/data/backups/rganapa/Sebastian/eecs116_projects/research/BASELINE_FINISH_REPORT.md).
- VINS-Mono `failureDetection()` thresholds: accelerometer bias norm >2.5, gyro bias norm >1.0, translation between solves >5 m, z jump >1 m; low features and large rotation only log; on failure `clearState(); setParameter()` — [estimator.cpp](https://raw.githubusercontent.com/HKUST-Aerial-Robotics/VINS-Mono/master/vins_estimator/src/estimator.cpp). The viobench patch also adds a "big IMU acc bias estimation" warning in the patched initializer (`VM/patches/vins_mono.patch` L297).
- IMU model in the simulator: accel bias init uniform +-0.2 m/s^2, bias walk 0.001; gyro bias init +-0.02 rad/s, walk 0.0006 rad/s/sqrt(s); noise 0.28 m/s^2 and 0.07 rad/s per sample at 200 Hz — `episode.json` config.imu in `/data/backups/rganapa/Sebastian/gen/raw-fast/selected/*.zip`.
- OV smoother has no per-frame check on the number of image factors; `optimize()` runs with whatever factors exist (`fixed_lag_vio.h` L429-486). MSCKF frontends only use a feature on 11,116/29,000 update frames in the old wrapper — [project_history.md](/data/backups/rganapa/Sebastian/eecs116_projects/research_notes/Drone%20VIO%20ATE%20approaches/project_history.md).
- FEJ rationale (standard EKF makes global yaw falsely observable; FEJ keeps the 4-DOF null space) — [OpenVINS docs](https://docs.openvins.com/fej.html).

## 3. False stationary updates

### Takeaway
For the provided OV the classic ZUPT problem is already switched off (ordinary zero-velocity detector disabled; `zupt_options.chi2_multipler = 0`); the live risks are (a) static init and the startup `rotation_update.h` zero-velocity constraint applied when the drone actually moves slowly, and (b) VM's stationary bootstrap and "rebuild stationary window" path. The old own-wrapper result (ZUPT fired on 17,548 of 19,490 frames moving >0.2 m/s) is not evidence about the provided baseline.

### Cited Findings
- Own upstream OpenVINS wrapper: stationary update off 2.843 / on 2.837 / inertial-only detect 2.881 on campaign30; ZUPT fired on 17,548 of 19,490 frames moving >0.2 m/s — [project_history.md](/data/backups/rganapa/Sebastian/eecs116_projects/research_notes/Drone%20VIO%20ATE%20approaches/project_history.md).
- Provided OV disables the ordinary detector ("its raw per-frame disparity test can mistake slow translation for rest and incorrectly absorb that motion into the IMU biases"); startup rotation updates add zero velocity while the rotation model fits (`OV/README.md`, `OV/rotation_update.h`; `OV/solution.cpp` L78, L95-96).
- Only 39/60 five-second crops start >0.1 m/s (hover or slow starts common); initial speed >=0.2 m/s group is the worst for OV capped30 (11.6 vs 4.2) — [BASELINE_FINISH_REPORT.md](/data/backups/rganapa/Sebastian/eecs116_projects/research/BASELINE_FINISH_REPORT.md), prior notes.
- An accelerometer cannot tell constant-velocity cruise from rest; only vision (disparity) separates them. OV's static init also asserts zero velocity with `init_static_sigma_ba = 0.2/sqrt(3)` (`OV/solution.cpp` L140). (Mechanism statement is my reading of the source.)

## 4. Textureless and dark ProcTHOR views

### Takeaway
Vision is blind for stretches that are statistically common in the pool (flat_fraction Spearman +0.59 to +0.61 with VIO ATE). The right fix is not better vision but graceful degradation: detect blindness, coast on N2 velocity (not on IMU double integration), and re-enter with a consistency check.

### Cited Findings
- Spearman of ATE with flat_fraction +0.61 (OV) and +0.59 (VM); with dark_fraction +0.35 and +0.48; OV mean 50 m on ProcTHOR versus 1.3-3.1 m on HSSD — [dataset_and_error_tail.md](/data/backups/rganapa/Sebastian/eecs116_projects/research_notes/Drone%20VIO%20ATE%20approaches/dataset_and_error_tail.md), [report](/data/backups/rganapa/Sebastian/eecs116_projects/reports/Drone%20VIO%20ATE%20approaches.md).
- OV frontends use `num_pts = 150`, `fast_threshold = 15` (`OV/solution.cpp` L105-106); VM uses Shi-Tomasi with spatial distribution; README already provides a bounded one-second retry without zero-motion constraints after dropout.
- Learned detectors find more repeatable points on low-texture walls than Shi-Tomasi per repo notes, but front-end swaps gave 5-7% in literature ([DL-VINS-Factory 2607.01757, unverified here](https://arxiv.org/pdf/2607.01757)).

## 5. VINS-Mono step failures (status -1)

### Takeaway
Two distinct sources: (i) deliberate throw at `VM/solution.cpp` L219 when the estimator reboots after metric output ("estimator reset after initialization; original camera frame was lost"), which is triggered by upstream `failureDetection()` (big translation >5 m, acc bias >2.5, gyro bias >1.0, big z >1 m), and (ii) other throws (nonfinite input, unusable Ceres solves "return an ABI error"). A reboot-and-reanchor policy converts (i) from a frozen trajectory into a bounded error. I did not run VM to count which cause dominates; the 10 flights >10 m in the pool should be checked for -1 status first.

### Cited Findings
- Failure path and thresholds quoted above (upstream `failureDetection`, `clearState`, `setParameter`, "system reboot!") — [estimator.cpp](https://raw.githubusercontent.com/HKUST-Aerial-Robotics/VINS-Mono/master/vins_estimator/src/estimator.cpp).
- viobench wrapper: after `processImage`, if `solver_flag != NON_LINEAR` and `state.output_ready` it throws; `step` catches and returns an error status (`VM/solution.cpp` L216-222 and L290-293). README: "A reset after metric output begins returns an ABI error because a fresh estimator would lose the original reference frame." Patch does not alter `failureDetection` (grep of `vins_mono.patch`: no hit).
- Evaluator behaviour after errors: hold last output; the baseline audit reports "zero filled frames" on completed runs; before the viobench improvement 4/8 recordings failed with 9,099 held frames (`VM/README.md`, table "Held frames after failures").
- Marginalization uses QR; unusable Ceres solves throw (`VM/README.md`).
- Also in the repo: provided VM tests 7 pass / 1 fail (hovering turn RPE 0.23884 > 0.15) — [BASELINE_FINISH_REPORT.md](/data/backups/rganapa/Sebastian/eecs116_projects/research/BASELINE_FINISH_REPORT.md).
- Pool VM stats: mean 5.506, median 0.621, 10 flights >10 m, max 225.6 m — [report](/data/backups/rganapa/Sebastian/eecs116_projects/reports/Drone%20VIO%20ATE%20approaches.md).

## 6. Yaw drift in the learned model's gyro-integrated attitude

### Takeaway
The measured floor (true velocity through our attitude: 0.967 m campaign, ideal yaw 0.209) says attitude, mostly yaw, caps the learned family. Vision-based bias is already at oracle level, so the residual yaw is the gyro's white-noise random walk (plus any bias miss) over a 60 s flight; it needs a yaw measurement, not a better bias. Of the yaw sources, Manhattan/vanishing-point anchoring looks weak in these scenes (my measurement), loop closure is nearly absent (my measurement), and the most promising cheap items are (1) visual rotation increments applied to attitude with a proper covariance, and (2) direction-of-translation correction of velocity (already built), followed by the VIO attitude when the VIO is healthy.

### Inferences
- With the simulator's gyro model, yaw from white noise alone is ~0.07/sqrt(200)*sqrt(60) = 0.038 rad (2.2 deg) 1-sigma at 60 s, and time-varying bias adds up to 0.0006*60^1.5/sqrt(3) = 0.16 rad (9 deg) 1-sigma at 60 s if bias were left uncorrected (my arithmetic). The oracle-bias arm removes the bias term, so the residual yaw floor is the white-noise walk; roughly 1-2 m of position error at ~1 m/s over 60 s and larger at 3-6 m/s (order-of-magnitude, my estimate), consistent with the 3.5 m pool score at high extent.
- Manhattan: expected benefit is small and unreliable here; the gates (>=8 lines, 55% agreement) would fire on only a minority of frames (per my sample), and it cannot fix yaw in non-Manhattan homes. Only a scoring run can settle it (cheap; already built).

## 7. Cross-cutting: do the suggested techniques fit this task?

### Takeaway
Ranked by expected mean-ATE leverage per engineer-day: guard/fallback, N2-seeded pre-init and origin, VINS re-anchoring, watchdogs, then init upgrades. FEJ, online time offset and loop closure are low value on this simulator; drag aiding hinges on a 0.5-day falsifier; Manhattan is conditional on scoring.

### Cited Findings
- Online temporal calibration is only useful with clock offsets; EuRoC ablation showed no clear gain from online dt (calibration good) while FEJ was a significant precision gain; in a simulation with bad initial calibration online calibration restored 0.139 vs 0.134 m (fork README, not peer-reviewed) — [classical_vio_survey.md](/data/backups/rganapa/Sebastian/eecs116_projects/research_notes/Drone%20VIO%20ATE%20approaches/classical_vio_survey.md). Simulator: mid-exposure timestamps, causal IMU windows, jitter <=1 ms in robustness tests.
- Rotor-drag model: Leishman et al. drag-force-enhanced model (rotor drag dominates accelerometer in horizontal flight; drag constant estimable in an IMU-only filter) — as described in a search summary of [arXiv 1510.03249 (Martin and Sarras, model-based observer using drag)](https://arxiv.org/abs/1510.03249); Xu and de Croon, "Efficient Model-Aided Visual-Inertial Ego-Motion Estimation for Multirotor MAVs", IMAV 2023 ([PDF](https://www.imavs.org/papers/2023/11.pdf)); I could not read its body text (PDF extraction failed), so no figures are cited.
- All three fusion components exist as wasm guests (VINS 3.4B, OV 4.0-4.35B, N2 1.7B peak fuel, cap 2e10 per frame) — [report](/data/backups/rganapa/Sebastian/eecs116_projects/reports/Drone%20VIO%20ATE%20approaches.md), [BASELINE_FINISH_REPORT.md](/data/backups/rganapa/Sebastian/eecs116_projects/research/BASELINE_FINISH_REPORT.md).

### Inferences
Suggested execution order (each step has a predeclared kill rule above):
1. Stage 0 (hours): offline replay of the output guard (1.1) and N2-origin substitution (1.2) on saved OV/VM trajectories; compute oracle-min bound.
2. 1-2 d: VM reboot re-anchoring (5.1) and VM/OV guard in code; fault-injection test.
3. 1 d: visual-factor watchdog + blindness coast (2.2, 4.1); learned-velocity veto on zero-velocity assertions (3.1).
4. 0.5 d each: drag R^2 falsifier, score structural guests, rot_essential on pool.
5. Only then: PNEC/DRT port (1.5), covariance inflation tuning (1.6), VINS threshold retune (5.2), attitude-from-VIO switching (6.2).
Not recommended: FEJ changes, online td, loop closure, DM-VIO port, Atlanta-world Manhattan before a pilot.
